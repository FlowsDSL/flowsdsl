# How `ReadFixedLength` macro is implemented

The way that hardware modules communicate is by exchanging fixed format messages on every step. They have a value regardless
of what's going on in the module. Ethernet module built into Flows runtime provides up to 4 bytes on every step in Data field
(populated from most significant byte to least significant), number of valid bytes in ByteCount (value of 0 indicates no new
data) and indicator whether it's end of the packet in Last field. Here's an example trace:

`ReadFixedLength` macro at 33:9 expands to (a bit simplified but keeps the general structure):

<pre>
ReadWhatPosition = 0;
while (true) {
  /* copy ByteCount bytes from incoming Network interface word into Headers bytes, starting at ReadWhatPosition, equivalent of:
   * memcpy(((unsigned char*) &Headers) + ReadWhatPosition, &Network.Data, Network.ByteCount);
   */
  ReadWhatPosition = ReadWhatPosition + Network.ByteCount;
  if (ReadWhatPosition >= 38) { HeadersAreComplete = 1; break; }
  if (Network.Last)           { HeadersAreComplete = 0; break; }
  step;
}
</pre>

The `ReadWhatPosition` variable (generated by compiler) can be seen counting up to 0x26 (38) bytes which is the total length of Ethernet (14), IP (20) and ICMP (4) headers.
Since Network interface provides 4 bytes per step it takes at least 10 steps to read the headers (in this case 12 steps due to 2-step gap, explained in the next section).

Headers is a struct but ReadFixedLength macro treats it as a simple 38-byte blob. Even though it looks in the tracing table like individual fields are being updated,
the entire Headers struct is recalculated on every single step using the current value and incoming bytes from Network interface (the table shows only changes in each
field on each step).

A planned improvement is to unroll the loop (in order to make it easier for SystemVerilog compiler implement it in hardware).

### Why is there a gap in Network Data input before 40004001?

There are steps where no new data is coming from the receive interface. These don't indicate gaps in the traffic. The link delivers data continuously, but the part of the
chip that converts it into 32-bit chunks runs slightly faster than the data needs, so now and then it has no new data to hand over. On those steps ByteCount is 0; one can
see that `ReadWhatPosition` stops increasing for two steps.

[Ethernet under the hood](Ethernet.md)
